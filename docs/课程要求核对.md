# 课程要求与数据库接入

核对依据：用户提供的《Web技术试验要求2026.docx》。核对及接入日期：2026-10-31。

## 选题与功能

大纲未指定项目题目、管理系统类型、最低表数量或最低功能数量。校园场馆预约管理系统可按该大纲提交，但最终成绩取决于实际验收、报告、演示及个人贡献，不能仅凭技术栈判断。

当前实现学生查询场馆、选择时段、提交与取消预约，管理员审核、维护场馆，以及签到、权限隔离和预约统计。用户注册、通知等扩展不是大纲列出的必做项。

## 三张表

| 表 | 用途 | 主要字段 |
| --- | --- | --- |
| `app_user` | 学生与管理员账号，共用一张表，通过角色区分权限 | id、username、password_hash、display_name、role |
| `venue` | 场馆资料与开放规则 | id、name、category、location、description、capacity、open_hour、close_hour、enabled、theme |
| `booking` | 预约及其审核、取消、签到状态 | id、user_id、venue_id、booking_date、start_hour、duration_hours、participants、purpose、status、created_at、checked_in_at |

用户与预约是一对多，场馆与预约是一对多，预约表的两个外键维护关系。密码存储 BCrypt 哈希。当前只保存最终审核状态，不记录每次审核人的操作历史；若以后增加审核追溯，再设计审核日志表。统计由预约数据计算，不必单独建统计表；当前无图片或文件上传，也无需附件表。

建表脚本为 `database/schema.sql`，只创建上述表，不创建或删除数据库。

## 本次接入结果

连接前，第 11 组数据库为空。建立 3 张 InnoDB 表后，初始化 3 个账号与 6 个场馆。通过应用接口完成“提交 → 管理员通过 → 学生取消”，并确认取消后时段恢复可用；保留一条标注“学校MySQL接入验证”的已取消记录作为联调记录。没有迁移本地 H2 历史记录。

本地 `.env` 保存连接参数，权限仅限当前用户读写，源码 ZIP 不包含该文件。后续 `bash scripts/start-backend.sh` 会读取它，使用学校库，默认不再初始化数据。单独运行 JAR 时不会自动读取根目录 `.env`，需先加载环境变量。

仍遵守用户“不上传学校提交网站”的要求。数据库接入只代表本机应用已能读写学校库，并不表示已经提交作业。

后续功能调整：预约时长为连续 1 或 2 小时，用途通过下拉选择，签到限定为预约学生本人。时长列迁移不会删除已有预约。
